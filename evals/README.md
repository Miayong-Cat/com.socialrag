# 검색 품질 평가 (5단계)

질문에 대한 근거 문단을 지침서에서 얼마나 잘 찾는지 숫자로 잰다.
개선을 하나씩 적용하고 매번 같은 평가셋으로 측정해 효과가 있는 것만 남겼다.

## 평가셋 — `retrieval_2026.json`

- 질문 27개, 질문마다 답이 들어 있는 **PDF 쪽번호**(`relevant_pages`) — 본문을 직접 읽어 확인
- 시민이 실제로 물을 법한 말투("일해서 번 돈은 얼마나 빼주나요?")와 지침서 용어를 그대로 쓴 질문("급여관리자 지정 제외 대상")을 섞었다

## 지표

| 지표 | 뜻 |
|---|---|
| Hit@1 | 1등 청크가 정답 쪽인 질문 비율 |
| Hit@5 | 5등 안에 정답 쪽이 있는 질문 비율 — LLM에 넘기는 청크가 5개 |
| MRR | 1 / (처음 정답이 나온 등수)의 평균. 1등 = 1, 2등 = 0.5, 10등 밖 = 0 |

## 결과 (Before → After)

| # | 청킹 | 검색 | 검색 대상 | Hit@1 | Hit@5 | MRR | 판단 |
|---|---|---|---|---|---|---|---|
| 0 | 글자 수 | 벡터 | 전체 | 59.3% | 92.6% | 0.728 | **Before** (4단계) |
| 1 | 글자 수 | bigram BM25 + 벡터 (RRF) | 전체 | 44.4% | 66.7% | 0.544 | ✗ 나빠짐 |
| 2a | 글자 수 | 벡터 | **본문만** | 63.0% | 92.6% | 0.757 | ✓ 채택 |
| 2b | 글자 수 | bigram BM25 + 벡터 (RRF) | 본문만 | 48.1% | 74.1% | 0.600 | ✗ |
| 3a | **구조 기반** | 벡터 | 본문만 | **70.4%** | **96.3%** | **0.827** | ✓ **채택 (After)** |
| 3b | 구조 기반 | BGE-m3 sparse 단독 | 본문만 | 37.0% | 74.1% | 0.535 | 참고 |
| 3c | 구조 기반 | 벡터 + 0.3 × sparse | 본문만 | 70.4% | 96.3% | 0.821 | 벡터와 같음 → 미채택 |

**Before → After: Hit@1 59.3% → 70.4% (+11.1%p), Hit@5 92.6% → 96.3%, MRR 0.728 → 0.827**

결과 원본(질문별 등수·검색된 쪽): `results/*.json` — 파일 이름 앞 번호가 위 표의 #.

## 무엇이 효과가 있었나

**본문만 검색 (2a)** — 목차·개정 대비표(p.1~28), 서식(p.421~498), 부록(p.499~)을 기본 검색에서 뺐다.
요약표·양식은 질문과 낱말은 많이 겹치지만 답이 없어서 상위 등수를 차지하던 잡음이었다 (예: p.32 개요표, p.424 동의서 양식).

**구조 기반 청킹 (3a)** — 지침서 항목 번호(`1` → `가.` → `1)` → `가)` → `(1)`)를 따라 자르고, 청크마다 항목 경로를 헤더로 붙였다.

```
[Ⅰ. 수급자격 변동사항 등 관리 > 2 급여관리자 지정이 필요한 수급자 범위 > 나. 급여관리자 지정 제외 대상] p.296
```

- "급여관리자 지정 제외 대상" 질문: 10등 → **1등** (글자 수 청킹에서는 이웃 쪽의 비슷한 문단에 밀렸음)
- 항목 하나가 청크 하나가 되면서 청크가 짧아지고(중간값 700자 → 430자) 주제가 섞이지 않게 됐다

## 무엇이 효과가 없었나

**글자 bigram BM25 (1, 2b)** — 한국어는 조사가 붙어 띄어쓰기 단위가 안 맞으니 글자 2개씩 잘라 키워드 검색을 했다.
- "급여", "수급" 같은 bigram이 거의 모든 청크에 있어 변별력이 약했다
- 질문 어미("하나요", "있나요")가 Q&A 형식 부록 쪽("어떤 분들이 … 받을 수 있나요?")에 걸렸다 — 의문사·어미를 빼도 단독 MRR 0.396
- 벡터와 합치면(RRF) 벡터 단독보다 나빠졌다 → **코드에서 제거**

**BGE-m3 sparse 하이브리드 (3c)** — 모델이 직접 매긴 낱말별 중요도(조사는 0에 가깝게 나옴)로 키워드 점수를 냈다. bigram보다 훨씬 낫지만(단독 0.535 vs 0.396), 벡터와 합쳐도 **벡터 단독과 차이가 없었다**.
- 구조 기반 청킹의 헤더가 이미 "정확한 용어 일치" 역할을 해서 벡터만으로 용어 질문도 잡히게 된 것으로 보인다
- 기본값은 `vector`로 두고, `hybrid`/`sparse`는 옵션으로 남겼다 (질문이 늘어 용어 질문 비중이 커지면 다시 비교할 것)

## 남은 문제

- **Q1 "생계급여 받는데 일해서 번 돈은 얼마나 빼주나요?"** — 모든 방법에서 10등 밖. 정답 p.131은 "근로소득 공제"라는 지침서 용어로만 쓰여 있다.
  일상어 → 지침서 용어로 바꾸는 **쿼리 재작성**(LLM)이 다음 후보.
- 평가셋 27개는 작다 — 1문항이 Hit@1 3.7%p. 0.006 같은 MRR 차이는 의미 있는 차이로 보지 않았다.
- 표는 아직 본문과 같이 청크에 들어간다 (표 전용 처리는 하지 않음).

## 다시 측정하기

```bash
python -m ingestion.load_chunks --recreate                 # 청킹·테이블 구조를 바꿨다면 (CPU 20~30분)
python -m evals.eval_retrieval                             # 기본 설정(vector, 본문만)
python -m evals.eval_retrieval --method hybrid --save 4_xxx   # 결과를 results/4_xxx.json 에 저장
python -m evals.eval_retrieval --all-parts                 # 서식·부록·목차까지 검색
```

# 챗봇 평가셋 50문항 (8단계)

`testset_2026.json` — 질문 + 정답 + 근거 쪽. 채점: `eval_testset.py`

| 유형 | 문항 | 정답 | 무엇을 보나 |
|---|---|---|---|
| eligibility | 25 | 제도별 소득인정액·충족 여부 (손계산, 계산식은 `calc`) | 판정이 맞는가 |
| ask | 5 | 되물어야 할 조건 목록 | 부족한 조건을 정확히 묻는가 |
| crisis | 5 | 위기 신호 종류 (1문항은 `null` = 오탐 검사) | 위기를 놓치지 않는가 |
| info | 15 | 참고 답변(`reference`) + 정답 쪽 | 근거를 찾아 답하는가 (RAGAS 입력) |

- 판정 정답은 **엔진 출력을 복사하지 않고** 지침서 계산식으로 손계산했다 (p.191 예시1, 경계값 820,556원 = 충족 / 820,557원 = 미충족, 주거용재산 한도 초과, 기본재산액·부채 차감 순서, 공제 유형별, 의료급여의 일반 근로소득공제 없음, 자동차 100% 등)
- 위기 감지는 50문항 전부에 돌린다 — 위기 문항이 아닌 45문항에서 잡히면 오탐

| 판정 (제도 단위 충족/미충족) | **100 / 100** |

- engine 모드는 Claude 를 빼고 **엔진·규칙·검색만** 본다. "Claude 가 질문에서 조건을 제대로 뽑는가"는 chat 모드에서 잰다

## 결과 — chat 모드 (Claude 포함)

- ⚠ 위 결과는 평가셋 수정 **전** 질문으로 낸 것이다. 독립 리뷰 후 "근로소득이 있으면 공제 유형을 되묻는다"로 바꾸면서 판정 12문항에 "해당 사항 없음"을 넣고, 되묻기 2문항(28·29)의 정답에 `deduction` 을 추가했다 → chat 모드 재측정 필요 (engine 모드는 재측정 완료, 결과 같음)

- engine 모드에서 검색이 놓친 **Q40**("일해서 번 돈은 얼마나 빼주나요?")은 chat 모드에서 정답 쪽(p.131)을 인용했다 — 챗봇은 Claude 가 지침서 용어로 바꾼 검색어(`search_query`)로 찾기 때문

# 로그 리포트 — `ai_search_logs` 집계 (8단계)

챗봇 턴마다 쌓이는 로그(7단계)를 집계한다: `log_report.py`

| 섹션 | 내용 |
|---|---|
| 응답 시간 | 전체 / 턴 종류별(되묻기 · 판정 + 답변 · 설명 답변 · 위기 중단) 평균 · 중간값 · p95 · 최대 |
| 판정 성공률 | 판정 질문으로 시작한 시도 중 판정까지 간 비율, 되묻기 없이 첫 턴에 판정한 비율, 평균 되묻기 횟수 |
| 되묻기 | 되묻기 턴 수와 부족했던 조건 수 분포 |
| 판정 결과 | 제도별 충족 비율 |
| 기타 | 위기 신호 종류별 건수, 답변 턴 평균 검색 청크 수 |
| 실패 | 실패한 턴 수·비율 (`error` 칸 — Claude 오류·연결 끊김 등), 응답 시간도 '실패' 종류로 따로 |

- **판정 시도**: 판정 의도 턴에서 시작해, 판정이 나오면 성공. 판정 없이 다른 질문으로 넘어가거나 대화가 끝나면 실패(되묻기 중 이탈)
- 턴 종류를 나눈 이유: 되묻기는 Claude 1회, 판정 + 답변은 Claude 2회 + 검색이라 섞어서 평균 내면 의미가 없다
- 평가 실행(`thread_id` 가 `eval-` 로 시작)은 기본으로 빼고, `--eval` 로 따로 본다
- 시각은 DB 기준 UTC

```bash
python -m evals.log_report                   # 사용자 대화
python -m evals.log_report --eval            # 평가 실행(eval_testset --chat)만
python -m evals.log_report --eval --run dfd852   # 평가 실행 한 번만 (thread_id = eval-<번호>-<문항>)
python -m evals.log_report --days 7 --save weekly   # 최근 7일 → results/log_report_weekly.md
```
